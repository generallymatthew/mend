- **`intake-app`: prompt caching on the system prompt, and sentence-streamed TTS -- the two real causes of "Thimble's reply is much slower than typing into Claude directly," reported live after the VAD/barge-in work above still didn't close the gap**:
  1. **No Claude call anywhere in `server.py` used prompt caching** -- `system=SYSTEM_PROMPT` was a plain string on all three call sites (`facilitator_reply`, `stream_facilitator_reply`, `stream_message_reply`), so every single turn reprocessed the whole ~8k-token system prompt from scratch before generating a single token, no matter how many turns reused the identical text. Fixed by defining `SYSTEM_PROMPT_BLOCKS` once (a content-block list with a `cache_control: {"type": "ephemeral"}` breakpoint) and passing that everywhere instead. Verified directly, not assumed: a raw API call showed `cache_read_input_tokens=9588, cache_creation_input_tokens=0` on a cached turn, and a two-turn streaming timing test showed first-byte latency drop 2.53s -> 1.69s turn-to-turn.
  2. **TTS waited for the ENTIRE reply to finish generating, then synthesized the ENTIRE thing as one `/api/speak` call, before any audio played at all** -- for a ~60-word reply this meant 6-9s of silence before Thimble's voice started, even though the text itself streamed in under 2s; the actual complaint was never the VAD gap, it was this.
