## Recently completed

- **Classifier per-class loss weighting, tried and honestly a mixed result, not a clean fix**: added `compute_pos_weight`/`WeightedTrainer` to `classifier/train.py` (per-class `pos_weight` for `BCEWithLogitsLoss`, computed from the train split only, `--no_pos_weight` to disable for comparison) to test the exact hypothesis `classifier/README.md`'s Results section raised — that `v4`'s cut_trigger regression came from training all 5 labels with equal loss weight regardless of how much each one's share of positives shifted between `v3` and `v4`. Retrained `v4` with it on: `immediate_safety_risk` recall did recover (0.33 → 1.0, the clearest casualty of the original regression), but cut_trigger F1 got *worse*, not better (0.81 → 0.76) — pos_weight fixed recall, which wasn't v4's actual problem; precision was, and pushing every under-performing class's recall up bought more false positives than the recall gain was worth, since cut_trigger is an OR across all four floor categories. Real, working mechanism, wrong lever for this specific problem — see the README's Results section for the full breakdown and what's worth trying next (a gentler weighting curve, or weighting only the class that was actually starved instead of all of them).
- **Live mode: two matching tiles (facilitator | you) in `intake-app`**: the facilitator's own spoken reply used to show up twice during a call — once as the caption/subtitle under its avatar, again as a full logged message in the side transcript panel. Live mode ("Go live") now swaps the single avatar + transcript log for two tiles, each with its own circle and a single current-sentence subtitle, mirroring the same one-place-per-speaker principle already applied to the employee's own live transcription. The employee's tile reuses that partial-transcription pipeline (mirrored into a new subtitle element); the facilitator's tile reuses the existing caption/chunking logic unchanged. Composer, mic-indicator dot, and transcript panel all hide while live, restored when live mode ends (including the "lost microphone access" exit paths, not just the manual button). Real bug found and fixed along the way: unsafe-centered flex content that overflows a box's *start* edge is invisible and unscrollable in every browser, which silently vanished the new facilitator label on a short/narrow viewport — fixed with `justify-content:safe center` on both tiles. Non-live Talk/Practice mode is unchanged. Verified both via direct layout-toggle calls and the real click → live-mode → real-speech-via-faked-mic path, at a realistic 1280x900 viewport.
- **Live partial transcription in `intake-app`, single-location display**: a first attempt at this showed live text in the mic-indicator label, then a separate final message once the turn ended — reported as confusing, the same content in two places. Rebuilt so a single transcript-panel bubble is created the moment recording starts (shown as "…"), updated in place as `POST /api/voice/partial` returns live partial text during speech, and corrected in place with the authoritative final transcript once `/api/voice` resolves — never duplicated. Still the torch-free approach (reuses the existing tiny.en/`beam_size=1` Whisper setup) over RealtimeSTT, whose torch/torchaudio dependency measured a real cold-start regression on this machine (~4 min) versus intake-app's current fast start. Verified live end-to-end in the browser via a faked `getUserMedia` (real speech audio piped through a decoded buffer, since the sandbox has no real mic).
- **Voice-memo latency in `intake-app`**, real fix not just relabeling: a voice memo turn measured ~30s end-to-end before this, and the UI blamed the whole wait on "transcribing..." even though transcription was a minority of it. Root-caused by direct profiling (not guessing): `/api/voice`/`/api/message`/`/api/start` were all synthesizing TTS audio inline before returning anything — TTS alone measured ~12-14s for a typical reply, the single biggest piece. `facilitator_reply()` now defaults to `synthesize=False`, returning text fast; a new `POST /api/speak` fetches audio in a second round trip the frontend doesn't block on, so the input re-enables as soon as text arrives instead of waiting on voice too. Also switched the OpenAI TTS model to `tts-1` (~2x faster than `gpt-4o-mini-tts`, less expressive voice, a real tradeoff). Separately, this dev machine turned out to be an old Intel MacBook Air (dual-core, no GPU/Neural Engine) — local Whisper transcription itself was measured at 5.16s for a ~9.5s clip, cut to 2.24s (tiny.en + explicit `cpu_threads`, both now the default) with no privacy tradeoff. A cloud STT option (OpenAI's `gpt-4o-mini-transcribe`, measured 1.81s) was deliberately not adopted — would send the employee's raw voice memo off the machine, a real step down for a product whose whole pitch is "nothing recorded," kept local-only on purpose even in this dev prototype. Combined result: `/api/voice` measured ~29.8s → ~6.6-7.1s in repeated live tests against the running server. Same fix now also applied to `post-session-app` (identical REST shape; was also missing the eager-startup-load fix entirely, and defaulted to `small.en` with no `cpu_threads` set, even slower than `intake-app`'s old default) and `joint-session-app` (WebSocket shape — `facilitator_reply()` never synthesizes inline now, a new `send_audio_followup()` fires via `asyncio.create_task` and pushes a separate `"audio"` event to the same recipient(s) the text `"message"` event went to, verified by reading the private-checkin routing directly and by a live two-participant WebSocket test: text arrived at +4.73s, audio followed separately at +8.11s, both participants getting identical content at each step). `joint-session-app` has no voice/Whisper input at all (text-only; real audio lives in `joint-session-audio/`), so only the TTS-staging half applied there.
- **Voice UI polish in `intake-app`** (mic feedback, VAD calibration, subtitle chunking, further transcription speedup): added a live "Listening" indicator (dot + label, lit by the same RMS level the VAD already computes) so it's visible whether the mic is actually picking up speech — previously "Go live" hands-free mode gave no signal at all. Fixed two real VAD bugs found by using it live: (1) noise-floor calibration tracked the *maximum* level in its first 400ms, so speaking immediately (the normal case in hands-free mode) poisoned the floor near the user's own speaking volume, cutting them off on ordinary between-word pauses — switched to tracking the minimum instead. (2) that wasn't enough alone: the calibration window also fully suppressed real speech detection for its whole 400ms, so the very start of anything said immediately was never marked as speech at all — redesigned so detection runs every frame from turn start regardless of calibration state, with calibration only refining the threshold in the background from genuinely-quiet samples. Known, accepted trade-off: a room with continuous ambient noise that never dips below the fixed floor can no longer calibrate upward around it, reintroducing a milder form of the original bug in that one case. Also fixed the "caption" subtitle overlay in the avatar/Talk view: chunking previously merged consecutive short sentences into one block up to a 90-char budget, so a reply's first few short sentences could all land on screen at t=0, before most of them were actually spoken — now one chunk is at most one sentence (a long sentence still splits further on clause breaks). Finally, cut further into transcription latency: `faster-whisper`'s own `beam_size=5` default measured ~30% slower on `tiny.en` than `beam_size=1` (greedy decoding) in repeated live tests, same transcript both ways — now the default in both `intake-app` and `post-session-app`.
