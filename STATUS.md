## Open observations

- **`intake-app`: mic-interrupt stuck-turn bug -- root cause confirmed, fixed.** Original live report: tapping the mic mid-reply (tap-to-interrupt) didn't immediately stop Thimble's TTS audio, and the resulting recording then took a very long time to transcribe (eventually succeeded, wasn't permanently stuck). Code half was cleared first: both interrupt paths (`talkMicBtn`'s tap handler and voice-triggered `interruptNow`, [static/index.html:3322](intake-app/static/index.html:3322)) already call the same `audioEl.pause()` + `stopBufferSource()` pair, confirmed live to stop playback with zero async gap on both playback paths (HTML element and Web Audio buffer) -- ruled out "the tap fails to stop playback in code." Acoustic half then confirmed with a real headphones-vs-speakers repro: same tap, same phrase, headphones on -- responded fine, no stall. Speaker echo (not code) was the cause, matching the standing `VAD_MAX_TURN_MS = 60000` ([static/index.html:3093](intake-app/static/index.html:3093)) hard-backstop theory -- residual sound still audible through the physical speakers right as the mic reopens was read by the VAD as continued speech, holding the turn open.
  **Fix shipped:** a new `INTERRUPT_MIC_SETTLE_MS = 200` delay between stopping playback and reopening the mic, on both interrupt paths (`interruptNow`, [static/index.html:3328](intake-app/static/index.html:3328); the tap handler, just above `startRecordingTurn(true)`). Gives the acoustic tail and the fresh stream's own `echoCancellation` a moment to settle before the mic goes live again. Verified live: timed `interruptNow` end-to-end, mic reopen fired at ~204ms after the interrupt, matching the delay. Not yet retested against the original speaker-only repro with a real mic -- next real test should confirm the stall no longer happens on speakers, not just that the delay fires.
- **`intake-app`: TTS silent-last-paragraph bug -- FIXED and verified, commit [dff941f](intake-app/static/index.html).** Original live report: the last paragraph of a long Thimble reply sometimes isn't spoken aloud. Root cause matched the original hypothesis: a failed/empty per-sentence `/api/speak` call was swallowed silently with no retry and no trace, and the trailing sentence is the one most likely to still be in flight when something transient (the OpenAI client's 8s timeout, [server.py:165](intake-app/server.py:165), or a dropped connection) hits. Fix adds one retry in `fetchSpeechAudio` plus a `console.warn` on final failure. Verified live in the browser: a forced-empty first response triggered an automatic retry that picked up a real URL on the second try; a forced always-empty response retried once, warned, and marked the item `ready` with `url: null` so the rest of the speech queue kept moving instead of stalling.
- **`intake-app`: live test showed Thimble flagging a harassment disclosure late, only after the user said something like "I got everything I need," not as soon as the described conduct met the mandatory floor.** Checked the code first: continuous per-turn screening is already implemented as designed (`maybe_override_via_voting` in [intake-app/server.py:498](intake-app/server.py:498), `screen_result` set fresh each turn by the model's own `<mend_signal>` block) and the system prompt is explicit that screening is continuous, not a separate step ([facilitator-intake-system-prompt.md:85](facilitator-intake-system-prompt.md:85), line 155). No code path waits for a session-end or closing-statement cue -- ruled out as the cause.
  Added a new diagnostic log to confirm/deny the model-confidence theory: `SCREEN_LOG_FILE`/`log_screen_signal()` in [server.py:428](intake-app/server.py:428), writing `intake-app/screen_signal_log.jsonl` on every turn (both `/api/message` and the real `/api/message/stream` path the UI actually uses). Deliberately logs ONLY `track`/`phase`/`screen_result`/`floor_triggered` + turn number, never the message text -- matches this file's existing "no conversation text" privacy boundary (see `ANALYTICS_FILE`'s own comment just above it), an explicit choice over logging full transcripts since this screens real HR disclosures. Confirmed live and working end-to-end.
  **Confirmed with a real retest:** turn 2 (first mention of the scenario) came back `screen_result: null` -- not even `"uncertain"`, a clean miss -- and only turn 3, after more was said, came back `floor_met` (`harassment_discrimination`). So the one-turn delay is real, not imagined. Can't yet tell whether turn 2 already contained enough to meet the floor and the model under-called it (a real prompt/model bug) vs. genuinely needed the extra turn, since the log by design never captures what was actually said. **Next step:** next time this is tested, keep a manual note of what was actually said each turn alongside watching `screen_signal_log.jsonl`, so the two can be compared without logging real disclosure text to disk.
