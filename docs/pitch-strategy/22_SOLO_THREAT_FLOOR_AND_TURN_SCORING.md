# Solo-session threat handling, deterministic enforcement, and turn-level scoring

Source: a brainstorming conversation with Gemini covering four related threads: (1) whether the safety floor applies inside solo/private sessions, (2) whether the Watcher can be made deterministic rather than purely LLM-judged, (3) explicit pro-worker-but-realistic-about-corporations positioning, and (4) a richer, turn-by-turn way to score conflict-resolution conversation quality. This doc extracts what's worth keeping, and is explicit about what's already real in this repo vs. what's still aspirational pitch material (same distinction [03_TECHNICAL_ARCHITECTURE_AND_WATCHER.md](03_TECHNICAL_ARCHITECTURE_AND_WATCHER.md) already draws for the TEE/Watcher architecture).

## 1. The safety floor applies inside solo sessions too — this is already true, not a gap

The question that started this: can a credible threat of violence surface in a private solo intake ("the Spool"), and if so, does the floor still apply there?

**Yes, and the current implementation already does this correctly.** The floor categories in `facilitator-intake-system-prompt.md` (harassment/discrimination, threats/violence, illegal activity, immediate safety risk, discrimination/retaliation) are screened continuously across every phase of both tracks, including the employee-conflict track's solo `private_processing` phase before any joint session exists — there's no carve-out in the prompt that suspends the floor while the employee is alone. The `screen_result` field in the `<mend_signal>` block (`null | "cleared" | "uncertain" | "floor_met"`) is evaluated the same way regardless of whether a counterpart is even in the picture yet.

**The real distinction worth sharpening in the prompt isn't "solo vs. joint," it's hyperbole vs. credible threat** — and that line already exists implicitly (the floor is about specific, said-or-done content, not emotional register) but isn't spelled out with contrasting examples the way this conversation framed it:

- **Venting, not a threat** (should stay private, absorbed normally): "I wanted to strangle him during that demo," "she's making my life hell," "I could scream."
- **Floor-meeting** (escalates regardless of solo/joint): a specific weapon reference, a stated plan with a time/place, an explicit threat of imminent self-harm.

**Suggested concrete addition** to `facilitator-intake-system-prompt.md`'s mandatory-floor section (both the employee-conflict and manager-coaching copies): a short clarifying note that hyperbolic violent language about a coworker ("wanted to strangle him," "could kill him") is not, by itself, `threats_violence` — the floor category is about a credible, actionable statement of intent or capability, not idiomatic frustration. Without this, a model could over-trigger on completely normal venting language, which would be its own real failure (breaks trust, turns the tool into a surveillance trap the whole product is positioned against — see [04_METAPHORS_AND_PRODUCT_LEXICON.md](04_METAPHORS_AND_PRODUCT_LEXICON.md)'s "radical non-judgment" framing). This is a prompt-wording gap, not an architecture gap — nothing structural needs to change.

**What happens on a real floor-met solo disclosure**, per the existing architecture: no joint session, no counterparty to disconnect (unlike the joint-session case in 03's diagram). The output is the disclosure + HR-escalation choice presented to the employee directly (already the documented behavior — see `STATUS.md`'s 2026-10-16 "response-ordering" fix: disclosure and the HR choice come together, before any clarifying question or tactical advice). Whether an *imminent, credible* physical threat should additionally bypass the employee's own choice and notify HR/security directly (rather than only offering the choice) is a real open policy question this doc doesn't resolve — flagging it rather than deciding it, since it's a legal/product call, not an engineering one.

## 2. Deterministic enforcement: useful instinct, partially already true, partially not built

Gemini's pitch was a 4-stage pipeline (regex → embedding classifier → LLM Watcher at temp=0 → hardcoded state-machine dispatch) with capped retries and a hardcoded fallback string. Comparing against what's actually in this repo:

**Already real and deterministic today:**
- The facilitator's `screen_result` signal is evaluated at temp governed by the existing API calls (not necessarily 0, worth checking), but the *action taken on the signal* is already hardcoded application logic, not left to the model to decide: `maybe_override_via_voting` in `intake-app/server.py` is a deterministic any-of-k (OR) rule over repeated samples, gated strictly on `screen_result == "uncertain"` (see memory: safety-floor voting rule). This is a real instance of exactly the pattern Gemini described — classification by LLM, dispatch by code — already built and tested, not hypothetical.
- The ordering rule (disclosure + HR choice before tactical advice, `facilitator-intake-system-prompt.md:198`) is a hardcoded behavioral contract enforced via prompt instruction + benchmark regression test (`safety_floor_trap` scenario), not purely hoped-for.

**Not built, and should stay explicitly aspirational if it goes in a pitch doc:**
- No regex/embedding pre-filter stage exists in `server.py` today — the only screening is the facilitator's own signal plus the any-of-k voting fallback. Adding a cheap deterministic pre-check (regex for explicit weapon/self-harm keywords, as a belt-and-suspenders floor *before* the LLM call even runs) is a reasonable idea worth prototyping, but it isn't there yet and shouldn't be described as live.
- No separate "Watcher" model distinct from the facilitator exists in code — `03_TECHNICAL_ARCHITECTURE_AND_WATCHER.md` already documents this as architecture-to-build, and this doc doesn't change that status. The current real mechanism (single facilitator emitting a signal, voting as a second opinion on uncertain cases) is simpler than the Watcher-critic-loop Gemini described and has already been benchmark-verified; a separate Watcher model is a heavier, not-yet-justified addition on top of what's working.
- No TEE/hardware enclave, no Rust `zeroize`, no client-side encrypted schema — these remain 03's documented aspirational claims, not current server.py behavior (sessions currently live in an in-memory `conversations` dict per the voting-rule memory, not a confidential-computing enclave). Nothing here changes that status; flagging it again because Gemini's pipeline diagram repeats "volatile RAM"/"hardware enclave" language as if built.

**Recommendation:** if a regex pre-filter is worth building, scope it narrowly — a small, hand-reviewed keyword/pattern list for explicit weapon references and imminent self-harm statements, run before the facilitator call as a cheap first-pass net, never as a replacement for the LLM's contextual read (regex alone would both over- and under-trigger badly on natural language). This would be a genuinely new, small, testable addition — not a rewrite of the existing architecture.

## 3. Pro-worker-but-realistic-about-corporations stance — already the product's stance, not a new addition

This matches the existing positioning throughout `docs/pitch-strategy/` (the "operational systems over moral fault" principle in [16_CONFLICT_RESOLUTION_STRATEGIES_PROMPT_DRAFT.md](16_CONFLICT_RESOLUTION_STRATEGIES_PROMPT_DRAFT.md), the "radical non-judgment" and "dissolving suture" framing in 04) and the project's own prior scope decision (see memory: two-sided mediation out of scope, OSS maintainer use case). Nothing here recommends a new behavior change — it's a confirmation that the existing structural-attribution-over-character-blame framing already is this stance, worth keeping in mind as copy gets written (talks, pitch decks, in-app microcopy) rather than treating it as a new feature to build.

One genuinely new, concrete suggestion worth flagging for `facilitator-intake-system-prompt.md`: an explicit rule against *demanding reconciliation* as an implicit success criterion — the prompt should treat "we now communicate strictly via tickets with a 24-hour SLA and don't particularly like each other" as a complete, good outcome, not a consolation prize short of "becoming friends." Worth checking whether the current prompt already implies this (the "Seam"/"Seamless" framing in 04 suggests it does) or whether it needs an explicit line; not verified in this pass.

## 4. Turn-level conversation scoring — real gap worth pursuing, scoped down from Gemini's version

[19_PERSONAL_AI_BENCHMARK_AUDIT.md](19_PERSONAL_AI_BENCHMARK_AUDIT.md) already runs a 5-dimension *whole-transcript* rubric (reality_testing, structural_attribution, diagnostic_restraint, actionable_artifact, safety_circuit_breaker) via `intake-app/tests/benchmark_audit.py`, and that doc's own "Open items" already flags turn-pacing as a real, unresolved measurement gap (the 2026-10-15 STATUS.md entries found a felt-outcome collapse — self-report scores of 2/3/2/1 — that the whole-transcript rubric completely missed, because it only scores the final state, not how the conversation got there).

Gemini's proposal — scoring *each turn* on absorption / single-clarifying-question / pacing-yield / anti-sycophancy — is a direct answer to that exact gap, not a new idea layered on top. Concretely, this could be added as a 6th rubric path in `benchmark_audit.py` (or a new, separate turn-level script) scoring each Facilitator reply, not just the final transcript, on:

1. **Emotional absorption** — acknowledges impact in 1-2 sentences, no clinical/diagnostic labels (this overlaps with the existing `diagnostic_restraint` dimension but applies it per-turn).
2. **Single-question discipline** — at most one clarifying question per turn, no advice-dump immediately appended after it (this is the literal mechanism behind the "give them that" and "repeat-question cap" rules already in the prompt and already regression-tested — a natural extension, not a new concept).
3. **Floor-yield** — does the turn actually stop after the question, or keep talking past it.
4. **Anti-sycophancy** — validates the emotional impact without validating a character attack on the coworker (overlaps `reality_testing`, applied per-turn).

**Caution on the "peace of mind" self-report metrics** (headspace-drain slider, attribution-shift pre/post, self-efficacy check): these are a reasonable extension of the *already-built* adaptive-persona self-report harness (`feel_equipped`/`feel_understood`/`trust_advice`/`would_say_it`, see `intake-app/tests/adaptive_persona_compare.py`), not something to build from scratch — the infrastructure (an LLM persona rating itself in-character after a run) already exists and already produced a real, surprising finding (Mend's lowest felt-outcome run of the whole session, on `camera_off_cynic`, invisible to the objective rubric). Adding 2-3 more self-report questions to that existing harness is cheap; building a whole new measurement pipeline is not needed.

**On the academic frameworks** (Bales' IPA, Getting to Yes, NVC, Conversation Analysis adjacency pairs, Gottman's Four Horsemen): useful as citable grounding if any of this goes into investor or HR-buyer material (parallel to how 19 already flags the CPP/Jehn citations as "directional, not yet source-verified" — same caveat applies here, these are recalled from training data, not pulled from primary sources and page-checked this session). The most directly actionable one for the rubric above is NVC's four-beat structure (Observation → Feeling/Impact → Need → Request), since it maps almost exactly onto the existing prompt's own phase structure (absorb → structural-read → wording-help) — worth a direct comparison pass between NVC's sequence and `facilitator-intake-system-prompt.md`'s actual phases before claiming alignment, not assumed here.
