joint-session-architecture.md

Why this can't sit on a vendor avatar API alone

Tools like Tavus or HeyGen give a managed pipeline: text/audio in, avatar video out. Fine for intake, where the facilitator only ever talks to one person. A joint session needs a buffer inserted between the two humans' audio streams, with the ability to drop content before it's delivered: that requires owning the transport layer, not renting a black-box one.

Per-participant pipeline

Runs twice, once for each employee, both directions, simultaneously.

mic audio→ streaming STT→ rolling transcript window→ fast classifier→ facilitator LLM
fast classifier (per-chunk, low latency) gates the delay buffer below · facilitator LLM runs on full context from both transcripts, drives TTS + avatar output

The components

Transport
Self-hosted WebRTC SFU
LiveKit or Daily. Each joint session is a room with three participants: employee A, employee B, and the facilitator, a server-side agent, not a human, with per-participant publish/subscribe control.
Delay buffer
Broadcast-delay pattern
Each employee's outbound audio passes through a short ring buffer, on the order of 1–2 seconds, tunable, before it's released to the other participant.
Real-time gating
Fast per-chunk classifier
Scores each rolling chunk against the "active, escalating, imminent" bar before the buffered audio is released. Crossing it drops the chunk before delivery, and the receiving party never gets it.
Severity read
Facilitator LLM, full context
"Rising tension" and "serious, not acute" don't need sub-second gating. Read by the same model running the session, off the fuller rolling transcript and conversational context.
Signal
Prosody / tone
Proof-of-concept validated, wired into the facilitator LLM as an additional read on escalation beyond words alone.
Output
TTS + avatar
Carries the facilitator's own conversational moves and turn-taking back to both employees, same model output driving voice and the Thimble avatar.

Session state machine

Three ways in, one way the session ever actually ends: the close looks identical regardless of path.

ACTIVE → PAUSED_CHECKIN
Facilitator senses rising tension, no trigger. Other participant sees a neutral "one moment" state, no content leak. Flagged participant decides: resume or end.
ACTIVE → WINDING_DOWN (silent)
Serious-not-acute content surfaces, floor-tripping but not happening live right now. The facilitator does not announce, accuse, or confront.
ACTIVE → WINDING_DOWN (hard cut)
Fast classifier fires on a buffered chunk. That chunk is dropped before delivery; session moves to winding down.
WINDING_DOWN → ENDED
Same routine-sounding close every time, no observable difference between an ordinary end and an escalation. Employees move to fully separate rooms; only now does the facilitator tell each person individually what was escalated and why.

No-persistence constraint

The same ephemeral-by-architecture rule from the data page, stated at the component level.

Everything above

Operates on ephemeral in-memory streams. STT transcript windows exist only long enough to feed the classifier and the facilitator LLM's context, then are discarded, not written to disk or a database.

The one narrow exception

The tamper-evident trigger record, category and timestamp, not transcript content, is the only thing allowed to outlive the live session.

Real limits, not solved

There's always some irreducible latency, speech-to-text, classification, and the cut itself all take real time, so the delay buffer shrinks the window, it doesn't erase it to zero.
It also adds a small amount of lag to the whole conversation, not just the risky moments, the same tradeoff real broadcast delay accepts.
Judging a partial, still-arriving utterance is harder than judging a complete one: this tier needs a much higher, narrower bar, or false positives cost real trust.
